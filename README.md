# 全景跟随 · Pano Follow

**在一块 360° 全景画面里找到人、一直盯住他，再在他身上跑动作识别。**

输入是影石 X5 的 USB Webcam 实时流（2880×1440 等距柱状全景，机内已拼接防抖）。
全景里人在哪个方位事先不知道（可能在你正后方、也可能在天花板附近），
所以这个项目的核心是**先找到、再锁住、然后每帧只盯那一小块**。

```bash
python -m pano.live --port 8790     # 实时页：左边全景（带跟随标记），右边抽出的视角
```

---

## 一、它是怎么工作的

```
X5 全景帧 (2880x1440 等距柱状)
      │
      ├─① 找人：在球面上按 yaw×pitch 撒一圈小图，逐个问"这里有人吗"
      │         （粗扫 8 方位 × 3 俯仰 = 24 个视角，配 fov 90° 覆盖 -85°..+95°）
      │         → 候选按得分排序 → 去重 → 逐个用重型模型复核
      │         → 复核通过才"锁" ← 这一步是关键：最高分 ≠ 可用的视角
      │
      └─② 跟住：每帧在 (yaw, pitch, fov) 处抽一张透视视角
                → 跑 MediaPipe holistic → 反推"人在画面里的哪个位置、多大"
                → 回写 yaw/pitch/fov，下一帧继续盯住他
                → 同时输出动作语义（眨眼 / 举手 / 头 roll / 张嘴）
```

关键在于**两级检测**，因为它们贵得不是一个量级：

| 用途 | 模型 | 为什么 |
|---|---|---|
| 粗扫 / 跟丢后重找 | `pose.Pose(complexity=0)`，**无状态** | 只要"有没有人、在哪"，越快越好 |
| 锁住之后的每一帧 | `LandmarkEngine`（holistic） | 要 468 点人脸 + 33 点身体 + 双手 + 语义 |

> ⚠️ 粗扫的检测器**必须是无状态的**（`static_image_mode=True`）。
> 有状态的跟踪器在冷启动时对同一张图会检 0 个点、被前一帧"预热"过才检得出 468 个 ——
> 拿它去扫一圈，得分完全不可比。这个坑踩过，写在这里。

## 二、真机实测（影石 X5，M2 Max）

`pano/demo/real_x5/0_X5实机原始帧_2880x1440.jpg` 是未改动的实机原始帧：

```
锁定成功  yaw=+101.8°  pitch=+48.4°  fov=70°  score=0.85
脸 468 点 / 身体 33 点，动作语义完整
```

注意 **pitch=+48.4°** —— 人不在水平线上，而在相当高的位置。
这正是为什么"只扫地平线"的旧做法必然找不到人（`tests/test_pano_real_frame.py` 把这个结论固化成了断言）。

实时页实测（X5 直连、检测每帧都跑）：

```
整条循环  14.9 FPS      定位(抽视角) 9–12 ms      动作检测 26–37 ms
```

## 三、性能：从 3.4 FPS 到 ~15 FPS

**量出来的瓶颈和直觉相反了两次**，这是这个项目里最有价值的部分：

| 环节 | 实测 | 结论 |
|---|---|---|
| 解码 2880×1440 | 8–15 ms | **不是瓶颈**（一开始猜 60–80ms，错了） |
| pose 探针 512px（**成功**检出时） | **116 ms** | ← 第一真凶 |
| `equirect_to_perspective` 抽一个 512 视角 | **76 ms** | ← 第二真凶（完全没怀疑它） |
| holistic | 30–45 ms | 后来的地板 |

**第一真凶：同一个问题问了两遍。** 稳态每帧原来跑
"512px pose 探针 + 224px fov 拟合 + 512px holistic"，而探针问的"人在不在"，
holistic 的答案里已经有了。改成直接用 holistic 检出的身体关键点反推方位与尺寸来闭环
（`PanoFollow._absorb_detect`），每帧从 3 次模型调用降到 1 次：**292ms → 100ms**。

**第二真凶：`_bilinear` 每次都把整张源图转 float。**
`img.astype(np.float32)` 对 2880×1440×3 是约 **149MB** 的临时内存，光这一步 76ms ——
比跑一次神经网络还贵。交给 `cv2.remap`（C++、直接吃 uint8、定点插值）之后
512 视角 **75.9ms → 41.7ms**。**教训：「取个色」可能比「跑模型」贵，别只盯着模型。**

另外三处：

* **跟随视角 512 → 384**：抽取 41.7ms → **10.4ms**，而 face 468 / pose 33 在
  192/256/320/384/512 **全都稳定检出** —— 白捡。
* **取帧+解码挪进常驻后台线程**（读 MJPEG、只留最新一帧）：把"取到一张图"的
  30–45ms 从关键路径上彻底移走（改为并行发生）。
* **跟丢先试局部**（上次方位附近 3×3，约 0.6s）才退回全球面（约 3.0s）。

> 还有一个可选旋钮 `--detect-every N`：抽视角和画图每帧都做，动作检测每 N 帧跑一次
> （跳过的帧复用上一帧 landmarks，并在 `PanoResult.detected` 里**如实标 False**）。
> 默认 1。**故意不设成默认** —— "眨眼/举手以一半频率刷新"是功能取舍，不该由代码偷偷替用户决定。

## 四、已知限制（不粉饰）

1. **跟随依赖下游那次检测**。为了省掉重复提问，跟住之后跟随用的就是 holistic 的结果；
   检不出身体的那一帧跟不动（会退回探针兜底）。
2. **"锁着"不等于"跟到了"**。人不在画面里时，跟随会保持 locked 直到 `max_misses` 帧
   （已从 8 降到 4）。所以状态栏把**跟丢计数**显式打出来
   （"跟丢中（连续 N 帧没检出人）"），不装作在跟。
3. **杂乱但没人的画面可能幻觉**。实测在**一张铺好的床**上，holistic 会把被子褶子
   检成一具 33 点的"身体"，而且 7/7 锚点全在画面内。所以快路径的分数必须用
   **躯干真实可见度**来算 —— 只用"关节有几个在画面内"会给这种幻觉打满分 1.00。
   已加 0.3 可见度门槛、把反推方位所需最少锚点从 3 提到 4，**但没有根治**。
   现有测试只挡住了纯色图（`test_no_false_positive`），挡不住杂乱图。
4. **重力/横滚没有补偿**。全景帧不一定水平（相机放在桌上时画面是斜的），
   所以 `shoulderTiltDeg`、`head.rollDeg` 这类**带方向的语义不可靠**。
   要做"把信息贴到真实房间地面/墙面"就绕不开先估重力方向 —— 这是下一步。

## 五、文件

| 文件 | 作用 |
|---|---|
| `pano/projection.py` | 等距柱状 ↔ 透视 的投影数学（`equirect_to_perspective` 是热路径，用 `cv2.remap`） |
| `pano/follow.py` | 跟随状态机：粗扫 → 复核 → 锁定 → 逐帧闭环；`annotate()` 画骨架/人脸/手 |
| `pano/live.py` | 实时网页（aiohttp）：全景带跟随标记 + 抽出的视角 + 状态面板 |
| `pano/__main__.py` | 命令行入口（可处理单帧或目录） |
| `pano/demo/` | 合成演示图 + `real_x5/` 实机原始帧与诊断图 |
| `tests/test_pano_follow.py` | 6 项：投影往返、方位约定、圆周平滑、任意方位找人、空场景不误锁、抽出视角跑通检测 |
| `tests/test_pano_real_frame.py` | 4 项：**用实机原始帧**验证（人也可能在 pitch +50°，只扫地平线必然找不到） |

跑测试：

```bash
pip install -r requirements.txt
python tests/test_pano_follow.py
python tests/test_pano_real_frame.py
```

## 六、依赖与出处

为了能独立跑起来，本仓库**原样带了三个来自姊妹工程 GestureMate 的模块**：

| 文件 | 出处 | 用途 |
|---|---|---|
| `Utils.py` | GestureMate | `extractLandmarks()`：把 MediaPipe 原始结果整理成关键点数组 |
| `LandmarkEngine.py` | GestureMate | holistic 封装（本人脸 468 + 身体 33 + 双手） |
| `webui/face_body.py` | GestureMate | 动作语义（眨眼 / 举手 / 头 roll / 张嘴） |

它们不是这个项目的产出，只是运行所必需的依赖，放在这里是为了让仓库开箱即跑。
`pano/` 下的代码、测试与文档是本项目的产出。

**实时取流**依赖姊妹工程 `x5-link`（把 X5 的 MJPEG 以 `127.0.0.1:8765` 暴露出来）。
`pano/live.py` 会自己去读它的 `/stream.mjpg`；相机没出帧时会自动退回
`pano/demo/real_x5/` 里的实拍帧演示，相机回来再自动切回实时。

> 启动 x5-link 有个坑：**必须用 LaunchServices 启动**，直接执行 bundle 里的二进制
> 拿不到 macOS 摄像头权限，症状是"设备能枚举、模式能查到、但永远 0 帧且不报错"：
> ```bash
> open -a /path/to/X5Link.app --args web --port 8765
> ```
